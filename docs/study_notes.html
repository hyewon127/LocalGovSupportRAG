PART 1RAG 기초: 개념부터 차근차근

LLM은 무엇이고 왜 지어낼까

LLMLarge Language Model, 대규모 언어 모델. ChatGPT, 이 프로젝트에서 쓰는 qwen2.5 같은 것. 엄청난 양의 글을 읽고 "다음에 올 단어"를 맞히도록 학습한 프로그램입니다.

LLM은 질문을 받으면 "이 다음에 가장 그럴듯한 단어"를 하나씩 이어 붙여 답을 만듭니다. 그래서 문장은 아주 자연스럽습니다. 문제는 두 가지입니다.

학습한 뒤의 일은 모릅니다어제 올라온 지원사업 공고는 학습 데이터에 없습니다.

모르는 것도 그럴듯하게 말합니다"그 사업은 최대 5천만 원까지 지원합니다"처럼, 사실이 아닌데 자연스러운 문장을 만들 수 있습니다.

Hallucination환각. LLM이 근거 없는 내용을 사실처럼 말하는 현상. 지원사업처럼 금액·기간이 틀리면 실제 손해가 나는 분야에서는 가장 피해야 하는 문제입니다.
쉽게 말하면LLM은 책을 덮고 기억만으로 시험을 보는 학생과 같습니다. 문장력은 뛰어나지만, 모르는 문제에도 자신 있게 답을 써 냅니다.

RAG = 오픈북 시험

그래서 학생에게 책을 펼쳐 주는 방법을 씁니다. 질문이 들어오면 먼저 관련 자료를 찾아서 LLM에게 같이 주고, "이 자료만 보고 답해"라고 시킵니다. 이것이 RAG입니다.

RAGRetrieval-Augmented Generation. 이름을 한 단어씩 풀면 Retrieval(찾아오기) → Augmented(보강한) → Generation(생성). "찾아온 자료로 보강해서 답을 생성한다"는 뜻입니다.
쉽게 말하면도서관 사서(검색)가 관련 책의 해당 쪽을 펴서 주면, 학생(LLM)이 그걸 보고 답을 쓰면서 "몇 쪽에 있음"이라고 출처를 적는 방식입니다. 자료에 없으면 "모르겠습니다"라고 쓰게 합니다.

문서를 찾는 두 가지 방법

RAG의 품질은 대부분 ①찾기에서 결정됩니다. 엉뚱한 자료를 주면 LLM도 엉뚱하게 답하기 때문입니다. 찾는 방법은 크게 두 가지입니다.

방법어떻게 찾나잘하는 것 / 못하는 것
단어 검색
BM25		질문의 단어가 문서에 몇 번, 얼마나 드물게 나오는지로 점수를 매김. 책 뒤쪽 "찾아보기(색인)"에서 단어를 찾는 것과 비슷"라이브커머스"처럼 같은 단어가 있으면 정확함
"실시간 방송 판매"처럼 다른 말로 물으면 못 찾음
의미 검색
kNN		문장을 숫자 좌표로 바꿔서(다음 절의 임베딩), 질문과 뜻이 가까운 문서를 찾음표현이 달라도 뜻이 같으면 찾음
고유명사나 정확한 숫자는 약할 수 있음
BM25단어 검색 점수 계산법의 이름. 질문 단어가 문서에 자주 나올수록, 그리고 그 단어가 다른 문서에는 드물수록 점수가 높습니다.
kNNk-Nearest Neighbors, k개의 가장 가까운 이웃. 질문 좌표와 가장 가까운 문서 좌표 k개를 찾는 방법입니다.

이 프로젝트는 둘을 섞어 씁니다. 이것을 하이브리드 검색이라고 부르고, 2부에서 어떻게 섞는지 봅니다.

임베딩: 문장을 지도 위 점으로

임베딩글을 숫자 목록(좌표)으로 바꾸는 것. 뜻이 비슷한 글은 비슷한 숫자, 즉 가까운 위치가 되도록 학습된 모델이 해 줍니다.

아래 그림은 문장들을 지도 위에 찍은 모습을 상상한 것입니다. 단어는 달라도 뜻이 같은 문장은 가까이 모이고, 관계없는 문장은 멀리 떨어집니다.

"실시간 방송으로 팔고 싶어요"에는 "라이브커머스"라는 단어가 없습니다. 단어 검색은 못 찾지만, 의미 검색은 두 점이 가까워서 찾습니다.

벡터숫자 여러 개를 줄 세운 것. 예: [0.12, -0.08, 0.33, …]. 임베딩의 결과물이 벡터입니다.
차원벡터에 들어 있는 숫자의 개수. 이 프로젝트의 임베딩 모델(ko-sroberta)은 768개의 숫자로 문장 하나를 표현해서 "768차원"이라고 합니다.
유사도두 벡터가 얼마나 가까운지를 0~1 사이 점수로 나타낸 것(여기서는 코사인 유사도). 1에 가까울수록 뜻이 비슷합니다.
쉽게 말하면임베딩은 모든 문장에 "뜻의 주소"를 붙여 주는 일입니다. 질문의 주소와 가까운 주소를 가진 공고를 찾는 것이 의미 검색입니다.

왜 문서를 잘게 쪼갤까

공고 PDF 하나는 수십 쪽이 되기도 합니다. 통째로 쓰지 않고 잘게 나누는 이유는 두 가지입니다.

LLM이 한 번에 읽을 수 있는 양에 한계가 있습니다이 한계를 컨텍스트 윈도우라고 합니다. 넘치면 잘립니다(3부에서 실제로 겪은 문제).

필요한 부분만 정확히 주는 게 답이 좋아집니다50쪽 전체보다 "지원 대상" 부분 한 쪽을 주는 편이 LLM이 헷갈리지 않습니다.

청크chunk, 덩어리. 긴 문서를 잘라 만든 조각. 이 프로젝트는 공고 650건을 약 4,900개 청크로 나눴습니다.
토큰LLM이 글을 세는 단위. 단어보다 작은 조각으로, 한국어는 대략 1~2글자가 토큰 하나입니다. "500토큰 청크"는 대략 850자 정도입니다.
컨텍스트 윈도우LLM이 한 번에 읽을 수 있는 토큰 수의 한도. 질문 + 자료 + 규칙이 모두 이 안에 들어가야 합니다.

검색엔진과 색인

청크 4,900개와 각각의 768차원 벡터를 매번 처음부터 비교하면 느립니다. 그래서 찾기 쉽게 정리해 두는 저장소를 씁니다.

OpenSearch문서를 저장하고 빠르게 검색해 주는 검색엔진 프로그램. 단어 검색(BM25)과 벡터 검색(kNN)을 모두 지원해서, 이 프로젝트의 모든 공고 조각이 여기에 들어 있습니다.
색인 (인덱스)검색하기 쉽게 정리해서 넣어 두는 것, 또는 그렇게 정리된 저장 공간. 이 프로젝트의 색인 이름은 idx_support_chunk입니다.
쉽게 말하면도서관의 책장과 도서 목록 카드입니다. 책(청크)을 꽂아 두고, 단어로 찾는 목록과 뜻으로 찾는 목록을 둘 다 만들어 둔 곳입니다.

프롬프트와 가드레일

프롬프트LLM에게 보내는 글 전체. 이 프로젝트에서는 "규칙 + 찾아온 자료 [1]~[5] + 사용자 질문"으로 구성됩니다.

규칙에는 "자료에 있는 내용만 쓸 것", "문장마다 [번호]로 출처를 달 것", "자료로 답할 수 없으면 '찾지 못했습니다'라고만 쓸 것" 같은 지시가 들어갑니다. 하지만 LLM이 규칙을 항상 지키지는 않습니다. 그래서 코드로 한 번 더 검사합니다.

가드레일도로 옆 난간처럼, 잘못된 답이 사용자에게 가지 않도록 코드로 거는 안전장치. 이 프로젝트는 LLM을 부르기 전과 후에 하나씩 둡니다.

잘 되는지 어떻게 알까

"잘 되는 것 같다"는 느낌은 믿을 수 없어서, 정답을 미리 정해 둔 질문 목록으로 점수를 냅니다.

평가셋질문과 그 질문의 정답 공고를 미리 짝지어 둔 목록. 이 프로젝트는 관련 질문 27개 + 같은 뜻을 다르게 쓴 질문 27개 + 관계없는 질문 6개입니다.
Hit@5정답 공고가 검색 결과 상위 5개 안에 들어간 질문의 비율. 80%면 10번 중 8번은 5위 안에서 정답을 찾았다는 뜻입니다.
MRR정답이 몇 등으로 나왔는지를 반영한 점수. 1등이면 1, 2등이면 1/2, 3등이면 1/3, 없으면 0으로 계산해 평균을 냅니다. 1에 가까울수록 정답이 앞에 옵니다.
출처 인용률답변 중 [번호]로 출처를 단 답변의 비율. 목표는 95% 이상.

수집과 전처리: 파일에서 글자를 꺼내 조각내기

기업마당(bizinfo.go.kr)이 공식으로 제공하는 Open API로 공고 목록과 첨부파일을 받았습니다. 웹 페이지를 긁어 오는 방식보다 안정적이고, 공고 ID·기간·대상 같은 값이 정리된 형태로 옵니다.

Open API기관이 외부 프로그램에 데이터를 주기 위해 열어 둔 창구. 정해진 주소로 요청하면 공고 목록을 XML 형식으로 돌려줍니다.
전처리검색에 쓸 수 있도록 원본 데이터를 다듬는 모든 과정. 여기서는 파일에서 글자 뽑기와 조각내기입니다.

파일 종류는 이름이 아니라 내용으로 판단

파일 이름 끝의 .pdf 같은 부분을 확장자라고 합니다. 그런데 .pdf로 받은 파일이 실제로는 한글(HWP) 파일인 경우가 있었습니다. 그래서 파일 맨 앞 몇 바이트에 들어 있는 "형식 표시"를 읽고 판단합니다.

매직 바이트파일 맨 앞에 들어 있는 고유한 표시값. PDF는 항상 %PDF로 시작하는 식이라, 이름이 틀려도 진짜 형식을 알 수 있습니다.

조각내기: 문장 중간에서 자르지 않고, 경계는 겹치게

500~800토큰(약 850~1,360자)씩 자르되, 문장 중간에서 끊으면 뜻이 망가지므로 문장이 끝나는 곳에서 자릅니다. 그리고 조각 경계에 걸친 내용이 양쪽 조각에 모두 남도록 앞 조각의 끝 100토큰을 다음 조각 앞에 겹쳐 붙입니다. 이것을 오버랩이라고 합니다.

색인: 조각 하나 = 문서 하나

OpenSearch에 넣는 문서 하나에는 조각의 글, 좌표(벡터), 그리고 필터용 정보(지역·분야·기간)가 함께 들어갑니다.

하이브리드 검색: 두 점수를 섞는 법

단어 검색 점수(BM25)는 0부터 수십까지 나오고, 의미 검색 점수는 0부터 1 사이입니다. 그냥 더하면 숫자가 큰 단어 검색이 결과를 다 가져갑니다. 그래서 먼저 두 점수를 같은 눈금(0~1)으로 맞춥니다.

정규화서로 다른 눈금의 값을 같은 범위로 맞추는 것. 여기서는 목록 안에서 가장 낮은 점수를 0, 가장 높은 점수를 1로 바꾸는 min-max 정규화를 씁니다: (점수 − 최저) ÷ (최고 − 최저).
가중치여러 값을 섞을 때 각각을 얼마나 중요하게 볼지 정한 비율. 0.4 : 0.6이면 의미 검색을 조금 더 믿는다는 뜻입니다.

2단 가드레일: 지어내지 않게 하는 두 개의 관문

임계값통과·차단을 가르는 기준 점수. 여기서는 0.75. 가장 비슷한 조각의 유사도가 이보다 낮으면 "관련 자료 없음"으로 봅니다.

처음에는 질문 10개로 임계값을 0.77로 정했습니다. 그런데 평가해 보니 공고 제목과 다른 말로 물은 정상 질문의 약 5개 중 1개(18.5%)를 막고 있었습니다. 0.75로 낮추자 정상 질문은 모두 통과했고, 새로 통과한 관계없는 질문 2개("아파트 청약", "개인 주택담보대출")는 LLM이 스스로 거절했습니다.

쉽게 말하면정상 질문을 막으면 사용자는 답을 잃고 끝나지만, 관계없는 질문이 1차를 통과해도 2차 관문과 LLM이 한 번 더 거릅니다. 두 실수의 무게가 달라서 0.75를 골랐습니다.

평가 결과: 숫자를 믿기 전에 편향부터

평가 질문을 만들 때 공고 제목을 읽고 썼더니, 질문에 제목 단어가 많이 섞였습니다(27개 중 20개). 실제 사용자는 제목을 모르므로, 같은 뜻을 제목 단어 없이 다시 쓴 질문 27개를 따로 만들어 함께 쟀습니다.

편향측정 방법 때문에 결과가 한쪽으로 쏠리는 것. 제목 단어가 섞인 질문은 단어 검색에 유리해서 점수가 실제보다 좋게 나옵니다.

다른 말로 물으면 단어 검색만으로는 37%로 무너지고, 의미 검색을 섞어야 88.9%가 나옵니다. 1부에서 본 "지도 위 점" 개념이 실제로 효과를 낸 장면입니다. (공고가 650건으로 늘어난 지금은 85.2%)

로컬 LLM 연결기: 네 번 재고 네 번 고치다

로컬 LLM인터넷의 유료 서비스가 아니라 내 컴퓨터(GPU)에서 직접 돌리는 LLM. 이 프로젝트는 Ollama라는 프로그램으로 qwen2.5 7B 모델을 돌립니다. "7B"는 모델 안의 숫자(파라미터)가 70억 개라는 뜻이고, 클수록 똑똑하지만 느립니다.

자료를 줬는데 "정보가 없다"Ollama의 컨텍스트 윈도우 기본값이 4,096토큰이라, 5,836토큰짜리 프롬프트 중 2,050토큰만 들어가고 나머지는 에러 없이 잘렸습니다. 한도를 16,384로 늘린 모델을 따로 만들었습니다(ollama/Modelfile).

출처를 번호 대신 이름으로규칙을 문장으로만 주니 "OO 공고에 따르면"처럼 썼습니다. 작은 모델은 규칙보다 완성된 모양을 보여 주면 잘 따라 해서, 답변 모양 예시를 넣었습니다.

예시를 그대로 베낌이번엔 예시의 "OO 지원사업"을 실제 사업명으로 바꾸지 않고 그대로 썼습니다. 무엇을 채워야 하는지 적힌 틀(<근거 문서 제목의 사업명>)로 바꿨습니다.

너무 쉽게 거절함"도움이 될 사업이 하나라도 있으면 안내하고, 전혀 없을 때만 거절"로 규칙 순서를 바꿨습니다.

PART 3문제 해결: 조용히 틀리는 것들

트러블슈팅 모음

트러블슈팅문제가 생겼을 때 증상을 보고 원인을 찾아 해결하는 과정. 발표에서는 "무엇이 어려웠고 어떻게 풀었나"를 보여주는 부분입니다.

공통점은 대부분 에러 메시지 없이 조용히 틀렸다는 점입니다. 그래서 숫자로 확인하는 습관이 중요했습니다.

1. 확장자는 거짓말을 한다 수집

증상
.pdf 파일인데 PDF 읽기가 실패
원인
내용은 한글(HWP) 파일. 공고 사이트가 이름을 잘못 붙여 줌
해결
파일 맨 앞의 형식 표시(매직 바이트)로 판단
배운 점
외부에서 받은 데이터의 이름표도 확인해야 한다

2. 같은 질문, 실행마다 다른 답 검색

증상
코드를 안 바꿨는데 평가를 다시 하니 점수가 85.2% → 81.5%
원인
점수가 똑같은 조각들의 순서를 정해 두지 않아서, 파이썬이 실행할 때마다 다르게 늘어놓음
해결
점수가 같으면 조각 번호 순으로 정렬. 실행 조건을 바꿔 가며 같은 결과가 나오는지 확인하는 테스트 추가
배운 점
"가끔 다르게 나오는" 버그는 재현 조건부터 만들어야 보인다

3. 고장이 "결과 없음"으로 보임 예외 처리

증상
검색엔진을 꺼도 챗봇이 "관련 공고가 없어요"라고 답함
원인
검색 함수가 연결 실패를 빈 결과로 바꿔 버림
해결
실패를 그대로 알리고, 화면에 "검색 서버에 연결할 수 없어요"라고 표시
배운 점
"없음"과 "확인 불가"는 다른 상태다

4. 조용히 잘리는 프롬프트 LLM

증상
자료 5개를 줬는데 LLM이 "정보가 없다"며 일반 상식으로 답함
원인
컨텍스트 윈도우 4,096토큰 초과분이 에러 없이 잘림 (5,836 중 2,050만 전달)
해결
같은 글을 한도만 바꿔 보내서 실제로 들어간 양을 비교해 원인 확정 → 16k 모델
배운 점
LLM이 이상하면 "실제로 뭘 받았나"부터 잰다

5. 효과가 0이었던 수정 LLM

증상
질문 조건 뽑기에서 LLM을 껐는데, 평가 숫자가 한 자리도 안 바뀜
원인
끄는 조건을 잘못 걸어서 실제 실행 경로에는 적용되지 않았음
해결
조건을 고치고 테스트로 확인
배운 점
고쳤는데 숫자가 전혀 안 변하면, 고친 게 적용됐는지부터 의심한다

6. 점수는 100%인데 이상한 답 프롬프트

증상
답변 제목이 "OO 지원사업"
원인
LLM이 예시를 베낌. 출처 번호는 붙어 있어서 인용률 점수로는 안 잡힘
해결
예시를 틀로 바꾸고, 베낀 비율을 새 지표로 측정 (1/26 → 0)
배운 점
점수는 재는 것만 본다. 실제 화면을 눈으로 확인하는 단계가 필요하다

PART 4복습

용어 사전

기초

LLM대규모 언어 모델. 다음 단어를 맞히도록 학습해 글을 만드는 프로그램.예: ChatGPT, qwen2.5
RAG찾아온(Retrieval) 자료로 보강해서(Augmented) 답을 만드는(Generation) 방식. 오픈북 시험.
Hallucination (환각)근거 없는 내용을 사실처럼 말하는 것.예: 없는 지원금 액수를 말함
프롬프트LLM에게 보내는 글 전체. 규칙 + 자료 + 질문.
토큰LLM이 글을 세는 단위. 한국어 1~2글자 정도.
컨텍스트 윈도우LLM이 한 번에 읽을 수 있는 토큰 수 한도. 넘치면 잘림.

검색

임베딩글을 뜻이 담긴 숫자 좌표(벡터)로 바꾸는 것.
벡터 / 차원숫자를 줄 세운 것 / 그 숫자의 개수. 여기선 768개.
유사도 (코사인)두 벡터가 얼마나 가까운지 0~1 점수. 1에 가까울수록 뜻이 비슷.
BM25단어가 얼마나 자주, 얼마나 드물게 겹치는지로 매기는 검색 점수.
kNN좌표가 가장 가까운 k개를 찾는 의미 검색.
하이브리드 검색단어 검색과 의미 검색 점수를 섞어 쓰는 방식. 여기선 0.4 : 0.6.
정규화 (min-max)눈금이 다른 점수를 0~1로 맞추는 것.
청크긴 문서를 자른 조각. 여기선 500~800토큰.
오버랩조각 경계를 겹쳐 붙여서 경계의 내용이 끊기지 않게 하는 것.
색인 (인덱스)검색하기 쉽게 정리해서 넣어 둔 저장 공간.
필터조건에 맞는 것만 남기는 거름망. 예: 분야 = 수출.
슬롯질문에서 뽑은 조건 값(지역·분야·대상).

답변 품질과 평가

가드레일잘못된 답이 나가지 않게 코드로 거는 안전장치.
임계값통과와 차단을 가르는 기준 점수. 여기선 유사도 0.75.
출처 인용률[번호]로 출처를 단 답변의 비율.
평가셋질문과 정답을 미리 짝지어 둔 목록.
Hit@5정답이 상위 5개 안에 든 질문의 비율.
MRR정답 순위의 역수(1등=1, 2등=1/2…) 평균.
편향측정 방법 때문에 결과가 한쪽으로 쏠리는 것.
데이터 누수평가용 정보가 개발에 새어 들어가 점수가 부풀려지는 것.

스스로 점검

먼저 답을 떠올린 뒤 펼쳐 보세요. 위쪽이 기초, 아래로 갈수록 이 프로젝트에 관한 질문입니다.

기초 1. LLM만 쓰면 왜 지원사업 챗봇으로 부족한가요?

학습 이후에 올라온 공고를 모르고, 모르는 것도 그럴듯하게 지어내기(hallucination) 때문입니다. 금액이나 기간이 틀리면 실제 손해가 납니다.

기초 2. RAG를 한 문장으로 설명하면?

질문이 오면 관련 자료를 먼저 찾아서 LLM에게 같이 주고, 그 자료만 보고 출처를 달아 답하게 하는 방식입니다. 오픈북 시험과 같습니다.

기초 3. 단어 검색과 의미 검색은 어떻게 다른가요?

단어 검색(BM25)은 같은 단어가 있어야 찾고, 의미 검색(kNN)은 문장을 좌표로 바꿔 뜻이 가까운 것을 찾습니다. "실시간 방송 판매"로 물으면 "라이브커머스" 공고는 의미 검색만 찾습니다.

기초 4. 문서를 통째로 쓰지 않고 청크로 쪼개는 이유 두 가지는?

LLM이 한 번에 읽을 수 있는 양(컨텍스트 윈도우)에 한계가 있고, 필요한 부분만 정확히 주는 편이 답이 좋아지기 때문입니다.

기초 5. Hit@5가 88.9%라는 건 무슨 뜻인가요?

질문 100개 중 약 89개는 정답 공고가 검색 결과 상위 5개 안에 들어 있었다는 뜻입니다.

프로젝트 1. 두 점수를 그냥 더하지 않고 정규화하는 이유는?

단어 점수는 0~수십, 의미 점수는 0~1이라 그대로 더하면 단어 점수가 결과를 다 가져갑니다. 둘 다 0~1로 맞춘 뒤 0.4 : 0.6으로 섞습니다.

프로젝트 2. 가드레일 두 개는 각각 언제, 무엇을 검사하나요?

1차는 LLM을 부르기 전에 가장 비슷한 조각의 유사도가 0.75 이상인지, 2차는 LLM 답변에 붙은 [번호]가 실제 자료 번호인지 검사합니다.

프로젝트 3. 임계값을 0.77에서 0.75로 낮춘 이유는?

0.77은 다른 말로 물은 정상 질문의 18.5%를 막았고, 0.75에서 새로 통과한 관계없는 질문 2개는 LLM이 거절했기 때문입니다. 정상 질문을 막는 쪽이 더 큰 손해라고 판단했습니다.

프로젝트 4. 인용률 100%인데도 답변에 문제가 있었던 사례는?

"OO 지원사업"처럼 예시를 베낀 답변입니다. 번호는 붙어 있어서 인용률로는 안 잡혔고, 화면을 보다 발견해서 새 지표를 만들었습니다.

프로젝트 5. 자동 갱신이 중간에 멈추면 어떻게 되나요?

저장이 모두 성공한 뒤에만 "처리함"을 기록하므로, 멈춘 공고들은 다음 실행에서 다시 새 공고로 잡혀 처리됩니다. 검색엔진에 다시 넣어도 멱등성 덕분에 중복이 생기지 않습니다.
